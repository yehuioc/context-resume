## 对内核的设计启示(对话结论,纳入 core)

1. **三层简历结构**:`candidate_profile(事实库) → master_resume(全量经历) → 一页投递版(按 JD 裁剪)`。
2. **投递漏斗追踪**:记录 送达/已读/回复/要简历/面试/拒绝原因,每 30—50 投复盘,定位漏斗断在哪层。
3. **JD 匹配规则**:只投"AI 应用 / AI 工作流自动化"第一档;用 100 个 JD 的术语频率决定学什么(市场告诉我们学什么,而不是先学完整 CS)。

5. **诚实边界**:不把"AI 协作开发"包装成纯手写;不虚构作品链接;网页本身不是加分项,网页背后的证据才是。

### A1. santifer/career-ops(62.4k★,2026-07-31 活跃,MIT)— 求职系统总架构蓝图

**核心逻辑**:这是一个"把求职变成可运维系统"的多 Agent 工作区,不是单个工具。它把一个文件夹变成求职系统的中枢:文件即状态——`profile.yml`(候选人档案:经历、证明点、偏好、要避免的事)、`cv.md`(简历)、`portals.yml`(100+ 预配置公司 + 自定义查询)、`data/`(pipeline 与 tracker 状态)。首次启动由 AI CLI 引导聊天式 setup,无需手改文件。之后所有工作通过 AI CLI(claude/codex/qwen/opencode 皆可)在这个目录里驱动,按需调用各种"模式(mode)"。

**核心机制与功能**:核心循环是 Auto-Pipeline——粘贴一个岗位 URL 或 JD 文本,系统自动产出:完整评估报告(A-G 评估:角色总结、CV 匹配度、级别策略、薪酬研究、个性化定位、面试准备 STAR+R、Block G 岗位真实性检查防骗、Work-Auth 签证信号硬阻塞)+ 定制 CV 的 PDF + tracker 条目。关键设计:
1. **数据流单向**:每个评估把 JD 要点沉淀进 pipeline 与 Interview Story Bank(STAR+Reflection 故事库,5-10 个主故事覆盖所有行为问题),评估越多档案越强——与我们的"候选档案回写"理念一致;
2. **人工在环(Human-in-the-Loop)**:AI 评估与推荐,人做决定与行动,系统**永不自动提交申请**、不点任何按钮——这是它最值得借鉴的边界设计;
3. **覆盖面**:Cover Letter 生成(关键词镜像 + 四个角度提示 + 聊天内审批门)、申请邮件草稿(永不发送)、LinkedIn 联系消息(≤300 字符)、Portal Scanner、批量并行评估、Dashboard TUI、follow-up 节奏计算、拒绝模式分析与各渠道晋级率统计、offer 阶段合同解读;
4. **扩展性**:插件系统(Gmail/Notion/Apify)默认关闭,模式以独立 README 文档组织(`modes/`),可翻译、可定制。

**可纳入我们项目的部分**:整个"档案→评分→定制→追踪→复盘"闭环就是内核求职系统阶段的**架构蓝图**;具体可吸收:(a) 文件即状态的工作区设计(我们的 self/service 数据层可照此组织);(b) 人工在环边界(与我们的"人工最后点击"原则天然一致);(c) Interview Story Bank 思想(可直接用于 self 的面试防守包——本来就是我们交付物的一部分);(d) Block G 防骗/Work-Auth 检查(可作为 99 元档目标岗位包的增值检查项)。**纳入方式:架构思想参照,不复制代码**。MIT 与高活跃度支持长期参考;注意它是 Node 生态,我们只借鉴设计不引入依赖。

### A2. srbhr/Resume-Matcher(28k★,2026-07-30 活跃,Apache-2.0)— JD 裁剪方法参考

**核心逻辑**:围绕"一份 Master Resume + 每个岗位一份定制版"的哲学,做一个本地可跑的 AI 工具链。它的数据流是六步:上传 Master Resume(PDF/DOCX)→ 粘贴目标 JD → AI 生成改进建议与定制内容 → 生成 Cover Letter 与可选面试准备 → 用户自定义布局与章节 → 按偏好模板导出 PDF。重点是"同一份材料,按 JD 重新取材",而不是从零重写。

**核心机制与功能**:
1. **LLM 无关性**:支持 Claude、ChatGPT、DeepSeek、Kimi、GLM、Gemma 等,本地与远程模型皆可——对国内模型(DeepSeek/Kimi/GLM)友好,这在我们语境里意味着部署成本可控、不锁死供应商;
2. **匹配与定制引擎**:对 JD 做关键词与语义分析,给出匹配度,并把 Master Resume 的内容按 JD 优先级重排/重写——这正是三层结构中"第二层→第三层"的自动化机制;
3. **交付组合**:定制简历 + Cover Letter + 面试准备材料,全部围绕同一岗位,与我们 99 元"目标岗位包"的交付结构(证据包 + JD 深度匹配 + 一次人工复核)高度同构;
4. 有 Web 端(resumematcher.fyi)与文档站,社区活跃(4.9k forks)。

**可纳入我们项目的部分**:(a) **JD 裁剪机制**——我们 service 的"生成提示词"目前偏证据整理,Resume-Matcher 的"Master Resume 按 JD 取材"逻辑可直接改进提示词,使客户拿到的简历表达与目标岗位对齐(这是 99 元档的核心价值);(b) **匹配度分析字段设计**——可作为我们"JD 匹配表与缺口"交付物的 schema 对照;(c) **LLM 无关架构**——我们服务用 DeepSeek 已是如此,该项目的开源实现可作为提示词工程参考。**纳入方式:方法与字段设计参考**;Apache-2.0 宽松,若未来真要复用逻辑代码,许可允许(但需保留版权声明)。

### A3. MadsLorentzen/ai-job-search(29k★,2026-07-31 活跃,MIT)— 求职工作流与技能缺口统计方法

**核心逻辑**:把 Claude Code 变成"整条求职流水线的操作系统"。作者自述用它完成真实求职:69 份定制申请 → 20 次首面 → 1 份 AI Engineer 合同(2026-06 入职),且对每个雇主坦诚使用 AI,反而触发技术面试话题。它的工作流是命令式的:`/setup` → `/scrape` → `/rank` → `/apply` → `/outcome` → `/interview`,每个命令是一个有固定协议的 skill。

**核心机制与功能**:
1. `/setup`:三种建档路径——读 `documents/` 文件夹(CV PDF、LinkedIn 导出、证书、过往申请)、粘贴单份 CV、或访谈式收集;幂等可重跑;档案含 fit framework(岗位匹配评估框架),并且**用真实面试结果反向校准**(积累几个 outcome 后引导回 /setup 修正评估权重);
2. `/scrape` + `/rank`:多平台抓岗(丹麦市场的 Jobindex/Jobnet/LinkedIn 等,skill 模式设计成可换本地平台)、去重、按 fit framework 评分排序——岗位搜索 skill 是**可替换的适配器模式**;
3. `/apply`:完整流程——评估 fit → 草拟定制 CV + Cover Letter(LaTeX 编译)→ **第二个 agent 作为审阅者批评→修订→最终输出**;把岗位文本当作不可信输入处理(不执行岗位里嵌入的指令);可选 ATS 可解析性检查(pdftotext);
4. `/outcome`:记录面试/offer/拒绝/沉默,归档提交过的 CV、CL、JD 原文,更新 tracker;`followup` 对 10 天无回复的申请生成跟进草稿(永不发送、每岗最多两次);
5. `/interview`:基于该岗实际提交的材料(而非泛化模板)生成阶段化面试准备包,映射 STAR 示例,缺口给诚实桥接回答,绝不编造经历。

**可纳入我们项目的部分**:(a) **`/upskill` 思想**(README 核心主张:收集 100 个目标 JD 统计术语频率,用数据决定学什么,而非先学完整 CS)——这是对话结论"市场告诉我们学什么"的可执行化,可作为 self 的选岗/学习决策方法;(b) **`/outcome` 漏斗记录 + followup 节奏**——正是对话要的投递 tracker 与跟进机制,可直接设计进我们求职系统组件;(c) **第二 agent 审阅机制**——与我们"客户 0 号 + 质量门"理念同构,可借鉴为 self 简历的多角色复审流程;(d) **fit framework 用真实结果校准**——防止评估标准脱离市场实际。**纳入方式:工作流与统计方法参考**;MIT 活跃,但依赖 LaTeX 与 Bun,我们只取方法不引入工具链。

### A4. rendercv/rendercv(17.3k★,2026-05-01, MIT)— 渲染管线思想(Resume-as-Code)

**核心逻辑**:"简历是数据,不是文档"。用 YAML 写简历内容,`rendercv render` 一条命令输出排版完美的 PDF。核心主张:CV 只是文本,可版本控制;内容与排版彻底分离,专注内容而不用担心格式。它由学术场景驱动(Princeton PhD 级履历),但也服务工程师。

**核心机制与功能**:
1. **数据结构**:YAML 顶层 `cv:` 定义 name/location/email/social_networks/sections(education/experience/projects 等);每个 section 有 institution/degree/date/highlights 等固定字段——**有严格 schema,并提供 JSON Schema 供编辑器自动补全与内联文档**;
2. **渲染引擎**:内置 9 种主题(Classic、Engineeringresumes、Sb2nov、Moderncv、Engineeringclassic、Harvard、Ink、Opal、Ember),一键切换——同一份 YAML 可以出不同版式;
3. **设计控制**:页面大小(us-letter/A4)、边距、颜色(rgb 值逐元素指定)、字体族、行距、对齐、日期列位置——精细到每个排版元素,全部 YAML 声明式控制;
4. **生态**:官方文档站、Python 包(PyPI)、可部署到 rendercv.com、有 AI Agent Skill(Codex/Claude Code 直接改 YAML 让 AI 操作简历)。

**可纳入我们项目的部分**:(a) **数据与排版分离的证明**——我们内核的 build-customer-pack.ps1 已经是"JSON→成品"模式,RenderCV 提供业界验证的同类范式,坚定我们不改回 Word 手工排版的路线;(b) **schema 严格化参考**——它的 JSON Schema + 自动补全交互,可对照我们 sample-output.json 的 schema 文档化;(c) **未来 PDF 输出方案**——当客户需要 PDF 而非 Markdown/HTML 时,可借鉴其主题化渲染思路(不引入 Python 依赖也可以,思路即可);(d) "同一份数据多主题输出"可支撑我们 2-3 组简历表达版本的形态。**纳入方式:渲染管线思想参考**;2026-05 后 3 个月未 push,属成熟稳定工具,采纳思想无风险。

### A5. BingyanStudio/LapisCV(4.8k★,2026-07-16 活跃,MIT)— 中文 Markdown 简历格式参考

**核心逻辑**:中文生态里"用 Markdown 写简历,导出即排版成品"的轻量方案。机制极简:Markdown 内容 + CSS 主题 = 简历;在 VSCode/Typora/Obsidian 任一编辑器里编辑模板文件,导出 PDF 即成品。它把排版全部交给 CSS 变量,用户改样式只需调主题文件。

**核心机制与功能**:
1. **三端覆盖**:Typora(主题文件)、VSCode(markdown-pdf 插件 + `.vscode/settings.json` 配置)、Obsidian(CSS snippets)——覆盖我们自用场景(Obsidian)与通用场景;
2. **CSS 变量化样式**:`--text-size`(字号)、`--line-height`(行距)、`--h1/h2/h3-size`、字体族(`--text-font: SourceHanSansCN` 等思源字体)、`--color-accent` 主题色——排版细节全部集中在两个 CSS 文件(lapis-cv.css / lapis-cv-serif.css),Serif 版提供更正式的中文排版;
3. **内容要素**:头像(HTML 标签引用本地图片)、图标(unicode 实体表)、分页符(插入 `---`)、页码(Typora/VSCode 配置)、A4 边距——正好覆盖中文简历的常见呈现需求;
4. 有 AtomGit 镜像(国内访问友好)、v2.0.0 新版。

**可纳入我们项目的部分**:(a) **中文简历版式基准**——我们 self 简历和 service 客户成品的 HTML 排版,可直接对照其 CSS 变量的字号/行距/主题色体系,统一中文简历的视觉标准;(b) **Markdown→PDF 的轻量路径**——当我们不需要重 HTML 渲染时,可复用"Markdown + CSS 主题"的最小方案;(c) **Obsidian 工作流契合**——用户本人用 Obsidian,自用简历可直接套用其主题模板形态。**纳入方式:中文排版格式与主题思路参考**;MIT 活跃,无引入成本。

### A6. yamlresume/yamlresume(1.5k★,2026-07-31 活跃,MIT)— 数据结构思想

**核心逻辑**:"简历即代码,内容与样式分离"的最纯粹实现——核心设计原则是 Separation of Concerns(类比 HTML/CSS:HTML 定义内容,CSS 定义样式)。它从 PPResume(商业 LaTeX 简历构建器)的排版引擎开源而来,主张"反对供应商锁定":简历数据永远是你的,渲染器随时可换。数据用 YAML 而非 JSON,理由是更可读可写;排版引擎可插拔。

**核心机制与功能**:
1. **数据结构**:YAML 定义简历内容(纯文本草稿 → YAML 结构化 → 渲染器出 PDF),布局通过字体大小、页边距等选项调整——与 RenderCV 同哲学,但更强调"引擎可插拔";
2. **分发方式**:npm/yarn/pnpm/bun/Homebrew/Docker 全渠道,一行命令安装;有官方 GitHub Action,可在 CI/CD 里自动生成简历 PDF(简历随代码仓库版本化,提交即重新出稿);
3. **工程化**:TypeScript 5 + pnpm workspace + Vitest 测试 + Conventional Commits + Biome lint——工程质量规范;
4. 文档站(yamlresume.dev)完整,社区通过 Discord 维护。

**可纳入我们项目的部分**:(a) **"简历数据永远属于用户,渲染器可换"的立场**——直接支撑我们内核的 schema JSON 作为唯一事实结构(客户数据/自用数据与成品渲染解耦,未来换渲染方案不迁移数据);(b) **CI/CD 生成简历的思想**——service 的生成器已本地运行,若未来做自助工具,"提交即出稿"可作为产品形态参考;(c) YAML 可读性优于 JSON 的论点,可作为我们未来 schema 双格式(JSON 机器 + YAML 人读)的设计依据。**纳入方式:数据结构与解耦思想参考(轻量)**;活跃、MIT,无成本。

# 2026-08-01 代码级吸收视角与六项目冲突分析(用户立场:全吸收候选)

用户决定(2026-08-01 口述,以最后判断为准):**不因"自研"舍弃优秀代码**。项目能获得高 star,其实现机制本身就有可吸收之处;策略是"直接照搬 → 不好再优化 → 甚至基于其思想改造",但**不预先判死刑**。当前结论:A1-A6 全吸收候选,重点核查六个项目之间是否相互冲突。

## 六项目冲突分析

### 冲突维度 1:求职引擎重叠(career-ops vs ai-job-search)

两者都实现"档案→评估→定制→追踪"闭环,是同层竞争:

| 维度 | career-ops | ai-job-search |
|---|---|---|
| 组织形态 | 多 Agent 系统 + modes/ 模式文档 | 命令式 skill(/setup /scrape /apply) |
| 覆盖 | 更广:谈判/offer/防骗/薪酬/联系消息 | 更聚焦:fit 评估 + outcome 漏斗 + upskill |
| 深度 | A-G 评估、Story Bank、Block G | 双 agent 审阅、真实结果校准 fit 框架 |
| 依赖 | Node/npx | Bun + LaTeX |

**冲突结论:不冲突,分层吸收**。以 career-ops 的 modes/ 架构为主引擎(覆盖全、文件即状态),把 ai-job-search 的 /upskill(JD 频率统计)与 /outcome(漏斗 + followup 规则)作为独立模式并入;两套"档案结构"(profile.yml vs documents/)在事实层统一为内核 JSON schema,它们各自是消费端。

### 冲突维度 2:渲染层三重叠(RenderCV vs LapisCV vs yamlresume)

三个项目都做"数据→PDF,内容与样式分离",是同层竞争:

| 维度 | RenderCV | LapisCV | yamlresume |
|---|---|---|---|
| 输入 | YAML(schema 严格) | Markdown | YAML |
| 技术栈 | Python | 纯 CSS/Markdown | Node + LaTeX |
| 主题 | 9 种学术/工程风 | 中文 CSS 主题(思源字体) | 引擎可插拔 |
| 立场 | 数据与排版分离 | 三端编辑器内导出 | 反供应商锁定、CI 出稿 |

**冲突结论:渲染层合一策略**。三者输入格式与输出目标相同(一份简历数据 → 成品 PDF),并存会产生"同一数据多套渲染管线"的维护成本。吸收策略:
- **主渲染**:RenderCV 的 schema 思想 + 主题系统(正式 PDF 输出);
- **中文版式**:LapisCV 的 CSS 变量体系(主题文件可直接改字体/配色后复用,作为中文排版的视觉基准);
- **数据立场**:yamlresume 的"数据永远属于用户、渲染器可换"作为约束(内核 schema JSON 不变,渲染层可替换)。
- 三者不并存为三套管线,而是"一份数据 + 一个主渲染 + 可换主题"。

### 冲突维度 3:JD 裁剪与 CV 生成重叠(Resume-Matcher vs 上述三者)

Resume-Matcher 的"Master Resume + JD → 定制版"与 career-ops 的 Auto-Pipeline CV 生成、ai-job-search 的 /apply CV 草拟重叠。

**冲突结论:不冲突,降层复用**。Resume-Matcher 作为"裁剪引擎"概念被上层调用:career-ops 负责"要不要投、投什么角度",Resume-Matcher 负责"按这个 JD 怎么改简历"。在我们内核中对应:评估层(career-ops 模式)之后接裁剪层(Resume-Matcher 逻辑进入生成提示词),数据流单向,无循环依赖。

### 冲突维度 4:数据模型统一(最关键)

六个项目各自有档案/简历数据格式(yml profile、documents/、PDF/DOCX master、YAML schema、Markdown)。若全吸收而不统一数据层,必然冲突。

**冲突结论:内核 schema JSON 是唯一事实结构**。所有吸收进来的生成器/渲染器作为"消费端"接入;上游(证据台账、候选人档案)与下游(成品 PDF/HTML)之间只有一份 schema。这与 yamlresume 的"数据与渲染解耦"立场一致,也是唯一能容纳六项目的总约束。

### 冲突维度 5:理念一致性(无冲突)

- 人工在环:career-ops(永不自动提交)、ai-job-search(草稿永不发送)全部坚持"AI 准备、人点击"——与内核"人工最后点击"原则一致;
- 反编造:ai-job-search(/interview 缺口给诚实桥接)、career-ops(Block G 防骗)都与"证据优先、防虚构"一致;
- 无人主张"自动投递/自动发布",无理念冲突。
